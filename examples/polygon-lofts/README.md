# Matched polygon ring loft examples

These source programs and independent expectations are fixed before C077 runtime implementation. They select source `0.10` / `polygon-loft-0.1`, Agent/0.10 and recorded GLB/0.10 under the [adopted decision](../../docs/language-design/polygon-loft-v0.1/ADOPTION.md). A freeze records intended behavior; it does not report executed product results.

The positive corpus includes constant solid and hollow sections, solid and hollow frusta, a three-section chamfer, concave boundaries, multiple openings, changing wall materials, declaration reordering, numeric boundaries, rigid local placement and finite count maxima. End caps close only the first and last sections. Every lower section's outgoing vertex region owns its two strip triangles. Terminal regions remain validated but emit no strip.

`authoritative-quarter-turn.ok` distinguishes the adopted triangle surface from linear polygon interpolation. Its +90-degree upper correspondence forms a 2 × 2 × 1 rectangular box of volume 4 and area 16. At mid-height, interpolated corresponding vertices would describe a different cross-section. The -90-degree case has valid endpoint polygons but intersecting strip diagonals; the 180-degree case pinches correspondence edges. Swapped keyed holes collide between otherwise valid endpoint sections. Each must fail source construction.

The two maximum cases separately cover eight sections with 32 vertices each and four sections with 64 vertices each. Both contain eight holes and reach 256 authored vertices, 540 triangles and 1,620 flat corners. Their source explicitly requests 2,000,000 operations and 80 seconds, which the execution host must separately authorize. The over-limit aggregate and per-section negatives use the same request so that the named domain error can be reached. These are predetermined resource settings, not measured successful executions. All other cases omit execution limits and retain 100,000 operations / 30,000 ms.

`parts.ok` defines an exact pinned reusable hollow-frustum component. `assembly.ok` creates two occurrences. Its repaired source changes one upper-hole vertex in the first occurrence from x=0.5 to x=0.25 meters. The first occurrence moves while its sibling stays still. Accepted source, sibling geometry and pinned module bytes must remain intact through an invalid edit and the subsequent exact repair. `generated.ok` uses keyed generation to construct three independently identifiable ducts with heights 1, 2 and 3 meters under a common moving parent.

Negative cases cover section counts, orders and station gaps; locally invalid rings; correspondence mismatches; absent cap, strip and terminal materials; palette limits; earlier source rejection; and valid source geometry that fails after binary32 conversion. The rounded-decimal station example intentionally rejects: the exact canonical binary64 difference between 1.001 and 1 is smaller than canonical binary64 0.001. No epsilon is substituted for the adopted comparison.

`expected.json` contains source coordinates, identities, material ownership, independent expected volume and area, exact rational volume, analytic control formulas, counts, bounds, PBR values, motion samples and exact repair strings. Endpoint areas use the shoelace identity. Volume combines endpoint area contributions with the specified strip determinants, without implementing cap triangulation. Named prism/frustum cases are checked against separate analytic formulas. The generator imports Python's standard library only; it neither imports nor executes OntoKin.

An independent delivered-byte checker must verify the complete end-cap domains, directed edge incidence, exact strip triangles, nonadjacent three-dimensional intersections, actual normals, palette values, volume, area and recorded motion. Counts, area, positive volume or triangle centroids alone do not prove a valid surface. Reordering equivalence concerns decoded geometry and materials; changed source text necessarily has a different source revision, so complete GLB byte equality is not expected.

`acceptance-freeze.json` binds every source, this guide, the independent expectations and the authoring generator by size and SHA256. Do not regenerate expected outcomes from a product failure. A later preparation correction must preserve the original freeze and explain its independent cause and new identity.

# Polygon extrusions with source-authored holes

These `.ok` examples and independent analytic expectations are frozen before C076 implementation. The explicit binding is source `0.9` / `polygon-holes-0.1`, Agent/0.9 and recorded GLB/0.9. The [adoption decision](../../docs/language-design/polygon-holes-v0.1/ADOPTION.md) defines keyed rings, exact topology and delivery requirements. The freeze records inputs and expected outcomes; it establishes no executed pass.

`square-hole.ok`, `two-holes.ok`, `concave-outer.ok` and `slotted-bracket.ok` describe editable solids with through-openings. Additional valid cases cover a concave hole, collinear vertices in separate rings, declaration reordering, an outer ring declared after a hole, mixed wall regions, zero holes, permitted bounds and rigid visual placement. The maximum case has eight holes and 64 total boundary vertices. It explicitly requests 400,000 operations and 80 seconds; its host must separately authorize those ceilings. All other examples omit execution limits and retain the ordinary 100,000-operation / 30-second defaults.

`parts.ok` is an exact pinned reusable module. `assembly.ok` creates two independent occurrences. `assembly-repaired.ok` changes one vertex of the first occurrence's opening; the sibling, stable keys and module bytes remain unchanged. `assembly-invalid.ok` moves one hole vertex onto the outer boundary and must reject atomically. `generated.ok` constructs three keyed instances with different depths and common parent motion. The `libparts` import alias is deliberately distinct from the reserved `parts` keyword.

`expected.json` records each ring's authored keys, roles, orders, points and outgoing wall materials. It fixes area, volume, surface area, cap/wall counts, palette, motion clocks, exact repair strings and unchanged sibling expectations. Geometry checks must establish actual cap coverage and open holes, opposite edge incidence and outward inner-wall normals; area or centroid checks alone are insufficient. Independent decoding must also verify PBR values, rigid placement and recorded motion.

Invalid cases isolate boundary touching/crossing, overlap, nesting, reversed winding, invalid ring roles/orders/keys, counts, coordinates, units, depths and missing materials. Four binary64-valid cases require delivery rejection when binary32 conversion collapses an opening or positive clearance, including after rigid placement. Earlier source bindings must reject the new ring constructs. Failed attempts and any later preparation correction remain separate records; do not rewrite frozen expectations to create a pass.

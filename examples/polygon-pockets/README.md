These inputs and analytic expectations precede C079 runtime implementation. Source `0.12` / `polygon-pockets-0.1`, explicit Agent/0.12 and recorded GLB/0.12 select the separate [pocket decision](../../docs/language-design/polygon-pockets-v0.1/ADOPTION.md). A pocket ends at a visible interior floor and retains a positive base. The freeze establishes intended source and outcomes; it reports no executed product pass.

The corpus contains 82 cases: 27 valid bodies, 50 source refusals and five source-valid delivery refusals. Positive inputs cover the rectangular reference, zero pockets, concave boundaries, several independent depths and floor materials, exact arithmetic boundaries, stable identities, reordered declarations, reusable functions, rigid visual placement and bounded maxima. A predetermined stepped-tray case supplies an additional shape outside the main reference family. Two literal source/0.8 companions establish zero-pocket geometry/normal/material stream equivalence; source provenance remains different.

`rectangular-pocket.ok` describes a 4 × 3 × 2 meter body with a 2 × 1 meter opening and a depth of 0.5 meter. The expected volume is 23 m³, area 55 m² and complete mesh size 28 triangles / 84 flat corners. The independent measurements use authored planar boundary areas and perimeters plus exact binary64 floor arithmetic. They do not import the product, construct a triangle mesh or treat production output as an expected answer.

`parts.ok` is a pinned reusable library. `assembly.ok` contains independent first and sibling occurrences. `assembly-repaired.ok` changes only the first instance's depth from 0.5 to 0.75 meter; `assembly-invalid.ok` requests a depth that reaches the bottom. The accepted sibling and pinned library must remain unchanged, and the invalid edit must preserve the accepted revision. `generated.ok` builds three keyed occurrences with separate pocket depths and common parent motion. Library content is bound by its actual SHA256 in each importing source.

The maximum-count and maximum-coordinate cases explicitly request 2,000,000 operations / 80,000 ms. All five precision-refusal cases use those same explicit requests so geometry refusal cannot be replaced by exhaustion of ordinary defaults. Their host must independently authorize the ceilings. Other cases omit execution requests and retain 100,000 operations / 30,000 ms. Computation time is separate from the one-second animation.

The five delivery refusals isolate collapsed pocket width, exterior clearance, inter-pocket clearance, clearance after rigid placement and a floor/top collapse after a large local Z translation. Every source input remains geometrically valid in binary64. Delivered binary32 coordinates must be inspected; an accepted top opening with a missing floor, a filled opening or a through-hole is incorrect.

`expected.json` records source boundaries, keys/orders, materials, depth/floor arithmetic, independent measures, face-domain counts, logical identities, intended rigid placement, motion clocks and exact repair text. Independent delivery checks must establish full domain coverage, opposite edge incidence, permitted contacts, normals, materials and actual floor geometry. Matching volume, a plausible image or triangle centroids alone cannot establish these properties. The listed checker adversaries require omitted/reversed floors, filled openings, overlap, swapped depths, material alteration and through-hole substitution to fail.

`acceptance-freeze.json` binds every source, expectation and authoring file to the separately published decision. Do not change a frozen input to obtain a passing implementation. Preserve an unsuccessful run and fix the implementation or propose a separately reviewed semantic revision. [AUTHORING.md](AUTHORING.md) gives the independent methods and their limitations.

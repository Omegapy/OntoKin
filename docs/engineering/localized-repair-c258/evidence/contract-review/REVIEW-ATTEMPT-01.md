## Blocking numeric claim

The proposal says eight ULPs cover a separately rounded binary64 normalization
route, but no error bound establishes that assertion. Listing products,
additions, square root and division is insufficient, particularly around
subnormal values and rounding boundaries. A 100-digit Decimal computation also
does not itself prove correctly rounded binary64 projections for every allowed
tuple. The comparison policy must not inherit an unproved guarantee.

Acceptable resolutions are a scoped derivation, a narrower admitted quaternion
subset, or an explicitly chosen finite comparison policy without the exporter
coverage guarantee and with a properly bounded reference calculation. Parent
confirmed that the last option is acceptable. One compact reference solution
uses Decimal only to propose a float, then compares exact q-component-squared
over norm-squared against squared rational midpoints to adjacent binary64
values. Exact midpoint parity determines ties. This verifies the represented
projection rather than assuming enough decimal precision.

## Resource condition for implementation

A 64-character numeric lexeme can contain an enormous exponent. Bound exponent
magnitude before Decimal-to-Fraction conversion or any unbounded power of ten.
This is a finite-resource condition, not a request for broader numeric support.

# C197: admit a second assembly family for a public comparison

Start only after C196 is accepted, integrated and verified on actual `main`.
Read [GOAL](../../../GOAL.md), [AGENTS](../../../AGENTS.md) and
[STATUS](../../../STATUS.md), then reconcile the current head, PRs, work scopes
and integration lease. Verify the C196 acceptance, source identities, complete
recorded evidence and resulting-main checks. Restore retained evidence to recover
context; do not repeat completed C193–C196 author, construction or scene trials.

## Question and bounded outcome

Can the existing language and an existing common backend express and deliver a
small reusable equipment-tray assembly well enough to admit a later paired
author exercise? This is a second task family, selected to exercise coordinated
dimensions, reusable definitions and preservation of an independent sibling.
It is not another stop-coordinate variation on the prepared carriage gauge.

C197 has two valid closing outcomes:

1. **Admitted:** a frozen public task, qualified common backend path, accepted
   baseline deliveries, independent regeneration and checked failure controls
   are ready for a later author exercise.
2. **Feasibility proposal required:** an identified missing semantic feature or
   substantial adapter/backend change prevents admission. Publish the bounded,
   versioned proposal and effort estimate described below, with no baseline
   exports or author dispatch beyond the reached gate.

Neither outcome establishes an authoring advantage. There are no timed authors
in C197, and this public qualification is not described as blind or unseen.

## First gate: establish feasibility from existing capabilities

Inspect the actual adopted specifications, implementation and backend contracts
before creating native output. Produce a concise feature-to-implementation map
covering:

| Needed capability | Evidence required before admission work |
| --- | --- |
| Typed dimensions and frames | Existing syntax/profile for lengths, positions and relationships; exact units and frame interpretation. |
| Reusable tray definition | An existing supported class, module or reusable construction mechanism with its dependency closure. |
| Independent instances | Stable, addressable left/right instances and their component identities; a scoped instance change must preserve its sibling. |
| Derived geometry | An existing supported way to derive base/wall placement and dimensions from the selected cavity and wall dimensions. |
| Common delivery | A real existing path from both routes into the same pinned backend, construction meaning and export settings. |
| Independent checking | A reader that can measure delivered geometry and stable identities without trusting the author's claimed dimensions. |

The finite C193 carriage adapter does not by itself establish a tray mapping.
Check its actual supported schema and the other available mappings. Do not
rename gauge roles or quietly extend an experimental namespace to admit this
different assembly.

If a language semantic change, a new general importer, a production backend, or
a substantial new adapter is required, stop before baseline exports. A change
is substantial here if it must add a new representation/relationship mapping,
interpret unsupported constructs, or introduce new runtime semantics rather
than connect already supported operations through an existing documented path.
Do not make those additions inside this qualification milestone.

Instead publish a versioned feasibility proposal that identifies the exact
unsupported requirement, proposed bounded mapping or language change,
dependencies, expected implementation and validation work, effort range and
assumptions, and the evidence needed for a later go/no-go decision. Distinguish
measured facts from estimates. Keep the complete product goal intact. A small
adapter proposal is not approval to build a general backend.

Proceed only when an independent reviewer agrees that the selected family fits
the existing semantics and common delivery path. Keep the review and exact
source/backend revisions in the record.

## Proposed family and later author task

Use two independently identified equipment trays instantiated from one reusable
definition. Each tray has a base and rectangular walls surrounding a named
rectangular payload or an explicitly delivered measurement proxy. Prefer the
smallest static formulation the feasibility map supports. Geometry may meet at
shared faces; do not count or represent the same corner material twice.

The later public author task will resize the cavity of only the left tray to
fit a differently sized payload while maintaining declared wall thickness and
clearance. The right tray must retain its accepted geometry, placement and part
identities. A later reuse request will add another supported payload size while
preserving the earlier selections. Freeze how the supported size is selected
and what constitutes preservation before any baseline export.

This family involves coordinated dimensions across several parts. It introduces
no contact, deformation, animation or live-physics claim. The author's source
remains editable and owns the design; an output mesh alone is insufficient.

## Freeze before any baseline export

Publish and independently review one exact input manifest and protocol before
starting either route. The freeze must identify:

- The public brief, nominal geometry, payload dimensions, both instance frames,
  component names, ownership, base/wall dimensions, cavity dimensions, and the
  initial repair and later reuse requests.
- Exact dimensional, positional and clearance tolerances, with a short basis
  tied to the geometry scale and delivery representation. State which identity
  and source-preservation requirements are exact.
- The authoritative baseline source/dependency closure for each route, the
  shared backend version and bytes, common construction/export settings, and
  any route-specific preparation supplied to the future authors.
- The expected accepted baseline geometry and sibling-preservation checks.
  Describe how the checker derives measurements from actual vertices,
  transforms and part identities rather than trusting source annotations.
- The independent checker and two predetermined delivered-output failure
  controls: insufficient payload clearance, and changed or missing right-tray
  geometry/identity. The controls must alter real delivered content while
  remaining suitable inputs for the checker.
- What independent regeneration must reproduce. Require the exact source and
  dependency bytes, supported identities and geometry. If the selected contract
  permits volatile provenance differences, list those exact fields and the
  comparison rule in advance. Do not add an exemption after a mismatch.
- A route-independent command and attempt ledger, equal finite execution
  allowances, outer deadlines and process cleanup, the prescribed export and
  regeneration order, expected receipts, and stop conditions.
- Accounting fields for preparation effort, native commands, elapsed time,
  failures and human interventions. Future author counts, model/settings,
  submissions, repair turns, provider tokens and costs must be separate fields.
  Use unavailable values where telemetry does not exist.

Do not begin native output generation while any required part of this freeze
or its independent review is missing. A corrected pre-export freeze must retain
the earlier version and explain the correction. After exports begin, changed
geometry, thresholds, mappings or acceptance rules require a separately reviewed
follow-up task; they cannot rescue this admission attempt.

## Bounded baseline qualification

Reserve at most **one baseline export and one independent clean regeneration
per route: four native exports in total, including failures**. Run the two
routes against the same frozen backend settings. No automatic retry is allowed.
No new authors or unrelated native simulations are authorized by this task.

Each operation must have a finite host allowance and an independently enforced
outer deadline. Record requested/effective budgets, observed work, complete
commands and completion or stop reasons. If a required gate fails or an export
times out, stop the remaining native work, retain the reached state and publish
the failure. Do not raise an allowance after seeing a failure.

On the actual deliveries:

1. Verify source, dependency and backend identities, then independently measure
   the tray, payload/proxy, cavity, walls, clearances and instance frames.
2. Verify component and instance identities and the predetermined unchanged-
   sibling expectations. Do not accept matching pictures as this proof.
3. Reopen the selected destination output using its actual receiving path and
   retain the checks appropriate to this static delivery contract. Record the
   receiving implementation and artifact identities.
4. Run both frozen failure controls through the same checker. Insufficient
   clearance and the changed/missing sibling must be rejected for the expected
   reasons. These controls operate on retained output copies and do not authorize
   additional native exports.
5. Regenerate each baseline from its exact editable source in a fresh output
   location. Apply the frozen determinism and identity rules. Preserve the
   submitted baseline and its original receipts.

Both routes must qualify. A route using a different backend, a checker that
accepts either failure control, incomplete output/source provenance, a changed
acceptance rule or failed regeneration blocks admission. Preserve the result;
do not substitute a hand-repaired artifact or quietly choose another task.

attempt ledger, actual artifacts, receiving and measurement receipts, negative
control results, regeneration comparison, known failures and admission decision.
Identify the actual branch/head, applicable local verification and resulting-main

reuse exercise; it does not dispatch authors automatically. Before that later
exercise, freeze equal author information/resources and the measured success,
effort and cost criteria. A broader 30–50-task study and any claimed comparative
benefit remain separate decisions. One qualified family or successful pair is
insufficient evidence of superiority.

Preserve the inherited **FAILED** legacy driver and supplemental tail,
**4,239 distinct passing methods**, and **thirteen torque-read methods NOT RUN**
after the unchanged 30,000 ms setup failure. Retain all other external and
compatibility gaps. Ordinary defaults remain **100,000 operations / 30,000 ms**;
no existing runtime, contract, fixture, tolerance, release gate or hosted-workflow
policy changes in this task. General contact, live destination physics,
production backend expansion and every unmet [GOAL](../../../GOAL.md) domain
remain open.

# Independent C257 ownership reader review plan

## Authority and independence

The scope is ownership observations for the existing C210 keyed-rack family.
It does not qualify follow constraints, hinge connections, parameters, actions,
revision transactions, rebuilds, native execution or a complete C255 observation.

The reviewer owns only this audit directory. Author files will remain unchanged.
No C255 expected semantic answers, producer sidecar, C256 expected-source helper
or author reader will generate the independent baseline. The source baseline
utility imports only the standard library and reads preserved original `.ok`
bytes obtained at main `23b1d2b5abafde6a5826827c30bc1bbf8552ff8e`.

`SOURCE-BASELINE.json` records actual declaration/key spans. It establishes
18 source occurrences, two scene roots and 16 ownership edges for each original
endpoint. The before/after change affects one length literal and leaves owners
unchanged. Artifact IDs remain unassociated until independent traversal of the
actual GLB JSON chunk. The baseline is finite lexical evidence, not a general
OntoKin evaluator or proof of accepted revision authority.

## Proposed author interfaces

The author has proposed four separate surfaces:

1. `observe_source_ownership(source_files)` derives declarations, expanded owners,
   actual byte origins and a computed source-bundle revision.
2. `observe_glb_ownership(raw)` reports untrusted node, source-mapping and program
   ownership claims from actual GLB bytes.
3. `compare_ownership(source_files, raw)` joins source observations to all bound
   artifact identity and ownership claims.
4. `read_bound_endpoint(repo, endpoint)` adds the original source/artifact hash
   admission to the same traversal and comparison.

Tests will use documented public outputs and typed refusals. Exact APIs and
limits will be recorded from the frozen candidate before execution. A test
that requires a documented unsupported topology will demand explicit refusal,
not an unrelated expansion of the author scope.

## Independent source baseline

Scene Demo declares `first` and `second` as root objects. Class Rack declares
the generated `fingers` parts. The first rack's key inventory is the exact
`three_mounts` helper's literal keys: lower, middle, upper. The second rack's
instance override supplies bottom, lower, middle, upper, top. Finger declares
ordinary part `blade`, so each finger owns its blade.

Neither the `parent_frame` parameter nor the `parent` fields in follow mounting
or joint flex determine ownership. Their actual source blocks are retained as
excluded-relation witnesses. GLB scene roots and baked world transforms are a
separate representation, and cannot be used to infer this ownership graph.

## Input and mutation provenance

Each attempt will preserve the candidate commit/tree, code/dependency SHA256,
original input hashes, mutation recipe, actual mutated input hashes, expected
outcome rationale, actual output/fault and complete command log. Failed attempts
remain in their own numbered directories. Corrected code gets a new attempt;
no previous failure is overwritten. Minimal mutation fixtures may be stored
directly; reproducible scripts and exact original bindings preserve larger
derived inputs without repeated full payload copies.

The independent GLB traversal will decode the container header, JSON chunk and
actual metadata directly with standard-library tools. It will not read the
semantic sidecar or invoke C255 expected semantic helpers. Source/metadata
agreement is measured separately from historical hash admission.

## Acceptance and stopping point

The candidate must demonstrate original ownership, full identity/source joins,
real origins, supported changed-input behavior and explicit bounded refusals.
Actual source/reader tests and unchanged C256/C255/C253/doc gates are owned or
assigned by the main integrator; do not broaden them without a changed input,
concrete failure, unresolved risk or repository requirement.

After concrete findings are resolved, freeze the independent evidence and return
an approval or precise blocker for the exact candidate. Integration, resulting-
main checks, branch cleanup and final ZIP delivery remain the main agent's work.

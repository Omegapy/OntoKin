## Complete funding requirements

For a fixed matched successful invocation schedule, let `N` be the whole-group misses that attempt a new angular-cache lookup, `H` its usable hits, and `C=N-H` the recalculations. Native stable-domain lookup costs one charge, a usable hit promotes for one, and a miss inserts for one. Before eviction or all other new work, new cache bookkeeping is `N+H+C=2N`. The direct local saving is therefore

`9H - 2N`.

If all `m` invocations share a single retained tuple, this becomes `7m-9`, not nine saved charges per repeat. A cold singleton loses two charges even before admission. The optimistic P11/L03 arithmetic maxima would become 152/75 before eviction, key/admission work, value retention and all nonlocal changes. No complete net result follows from those illustrative maxima.

The required disjoint event ledger must include:

| Event family | Required accounting |
| --- | --- |
| Entry and key | Every additional field access or copied logical occurrence, type/domain/authority check, proof-method identity and key construction; a compound label is not a priced operation |
| Lookup | Every reached lookup; successful or cancelled promotions; actual operand-scope reset work and reentrant behavior |
| Cold calculation | The actual nine ordered arithmetic events, their input/prospective/result guards, and three range checks; preceding positional addition stays outside the unit |
| Publication | Each attempted insertion, promotion/eviction if reached, retained result occurrence and admission comparison; failed or partial calculations publish no success |
| Warm use | Current input/domain/authority obligations and retained-result use/copy; current lowered-domain or callback failures must not disappear |
| Refusal and repetition | Already spent optional work, retries, rejected admission, repeated misses after eviction, and any restoration/replay; no refund or cache-retention assumption |
| Shared-cache effects | Changed occupancy/order in the existing at-most-256-entry cache, displaced whole-group and nested entries, new/lost outer hits, changed arithmetic invocations, and reader-entry cache state |
| Downstream execution | Every resulting extra or avoided producer and independent-reader event, with reader mathematical authority remaining independent |

`ReachExecutionWork.lookup/remember` (reach_numeric.py:120–182) charge callbacks before cache mutation and can decline insertion or turn a candidate hit into a miss after domain changes/reentrancy. `_sync_cache_operand_limit` (248–260) adds a charged reset when required. Costs therefore cannot be derived solely from a nominal lookup/insert count on hostile or changing paths.

For a general completed source-matched request, an exact accounting form is `9*(B-C) - K - A - F - delta_other`, where `B` and `C` are actual complete angular computations in baseline and candidate, `K` is added cache bookkeeping, `A` all other new key/guard/authority/retention work, `F` separately counted restoration/replay, and `delta_other` is candidate minus baseline work outside these terms. `delta_other` is signed and unproved; it must not be replaced with zero or treated as a beneficial credit. Partial/refused executions require their actual reached event prefixes rather than nine per attempted calculation. This is an accounting identity conditional on a valid correspondence, not an authority-safe schedule or an established positive premise.

The reader uses a distinct `reach_independent_bounds_v1` namespace in `_Bounds.reuse` (reach_conformance.py:72–100), but shares the same work cache. Namespace separation prevents direct writer-result authority, not cache contention. Equal writer outputs can still change later reader work by changing entry occupancy/order. A fixed-reference-string LRU argument is insufficient because outer cache hits determine whether nested reference strings are executed.

The scope is precise: the direct nine-call reduction alone cannot rescue these two original requests if all other work/bytes/cache behavior is matched. It is not a measured completion cost, an executed tail, an impossibility result for a different algorithm, or a theorem bounding favorable shared-cache effects. Any claimed additional savings from changed cache behavior need their own complete proof and count.

## A more substantial next source target

The existing whole `certificate_group` key contains `bound: MotionBound`, hence `bound.speed`. `_certificate_quantities` does not use that speed in a numerical result. Its `rounded_bound` constructor forwards it at lines 1095–1096, but `complete_interval_bounds` decodes only `bound.acceleration` and `bound.angular_speed` at lines 1381–1382. That downstream function does use `enclosing.speed`, so the two must not be confused. All other whole-group arguments have visible numerical uses.

A distinct bounded next investigation can ask whether projecting only this unused speed component out of the existing key safely merges actual whole-group misses. A successful new whole-group hit would skip the full calculation, including the angular region, 21 outward-conversion calls, destination bounds and complete interval arithmetic. It would reuse the existing cache path and capacity rather than adding an angular-cache namespace. This gives a larger potential unit of work while avoiding the new entry family reviewed here.

That proposal is not yet safe, funded or selected for implementation. It must preserve the original `MotionBound` hash/equality and foreign-dispatch path where those are observable; authenticate whichever native scope permits the projection; price actual projection/normalization and copies; prove lowered-domain/first-error behavior; identify duplicates where every retained key component agrees; and include adaptive cache and reader effects. The same missing exact whole-key sequence remains an observation gap. A source-level proof that `bound.speed` is unused is sufficient to justify this next feasibility question, not instrumentation or a claimed speedup. No runtime or semantic change is approved by this review.

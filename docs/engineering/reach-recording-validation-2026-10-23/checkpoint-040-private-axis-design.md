## One concrete candidate: private selected-accessor axis + aggregate division-counter witness

The proposed design is **not** an additional immutable copy of the entire 206-row axis.

1. **Materialize once, privately.** At the original per-channel `times = [row[0] for row in decoded.accessor(sampler["input"])]` construction in `read_glb`, a private variant would materialize a tuple *instead of* that ephemeral list for one chosen channel, retaining the same decoded binary32 float values. The original nonnegative/strict stored-order predicate must execute against that exact tuple at the same source-control point. Its lifetime is extended only within the ongoing `validate_reach_export` request. Do not put a trustworthy flag on public `DecodedGLB`, its mutable `document`, `_cache`, or `_clocks`.
2. **Bind the selected accessor.** The helper chooses `animation["samplers"][0]["input"]`, which is not necessarily the input of the first channel. The private candidate is admissible only if its proven channel input equals that exact selected accessor and **every** sampler uses that same input identity; otherwise take the literal original helper. An unreferenced first sampler therefore cannot be admitted. Preserve each existing `independent_common_clock` work charge and each sampler's equality obligation; the private variant compares the proven immutable axis when identity is established rather than assuming a mutable public cache is authoritative. Multiple accessor IDs, even if values happen to be equal, take the ordinary path. The public `read_glb`, `DecodedGLB.clock` list return and direct/custom-reader `verify_retained_clocks` semantics remain untouched.
3. **Use a nonexported capability.** Only the native internal `validate_reach_export` path could receive a locally held tuple/accessor receipt. Do not allow a caller-created token, metadata flag or subclass property to claim proof. A `try/finally` must retire it on normal return, diagnostic, cancellation and any other exception. Precharge required receipt retirement before publication if an eventual cleanup charge could suppress the original exception.
4. **Honor the existing stage order.** The original `read_glb` validations finish before `verify_numeric_bases`, `program_metadata`, `build_reference` and `_verify_metadata`. Those stages must retain their precedence and calls. Eligibility must therefore cover the entire intervening proof lifetime, not just the moment the reader built a tuple. Reordering the clock check earlier is **not** this candidate.
5. **Witness the authored operand domain.** Capture `independent_exact_div` from the request's real `ReachExecutionWork.counts` immediately before the retained row loop and again after its last successful row. The row loop still executes every original `independent_retained_clock` charge, exact parse/reduction, authored label equality, stored binary32 cell test, semantic-label test and independent shift subtraction. A successful ordinary rational midpoint fallback always performs an upper-midpoint `_Bounds.div`, charging `independent_exact_div`. No division occurs in the native integer-cell route. Thus an authentic unchanged counter, with no reentrant mutation, would establish that every successful row used the native <=1,024-bit numerator/denominator route. Require the stable native full 32,768-bit operand cap throughout; smaller, changed or foreign domains take ordinary fallback. A merely equal counter in an untrusted dictionary is **not** that witness.
6. **Use the original ending sequence.** The authored endpoints `authored[0] != 0` and `authored[-1] != end` are checked first. The integer-cell domain and a distinct strictly increasing stored binary32 axis then imply strictly increasing authored clocks, with no need to evaluate the `any(_Bounds.compare(...))` loop. Only then are the existing semantic-boundary subset and time-tolerance checks executed. An ineligible or invalid receipt takes the original adjacent comparisons, including all first-failure behavior. A singleton axis is ineligible because it saves nothing.

**Mathematical proof obligations.** C039 already established the exact binary32 disjoint-rounding-cell implication, including the subnormal/zero/overflow edges and ties-to-even. For this candidate, the additional domain lemma is straightforward: two reduced exact rational row operands each having numerator and denominator at most 1,024 bits require at most 2,048 bits for either prospective cross product in `_Bounds.compare`. This is below the unchanged 32,768-bit admission cap. Both the row-cell proof and the category witness must be authentic. Do not infer small pairwise guards from clock membership alone.

## Why the required receipt cannot yet be authenticated cheaply

### Source and dispatch authority

`DecodedGLB` is a mutable dataclass. Its JSON document, accessor data, clock lists and callbacks are mutable, and the original reader's per-channel temporary list is not an invocation-owned immutable proof. The internal function must prove that the privately retained tuple is the current actual selected input at the helper call **after** all intervening stages. Before trusting it, the gate must also cover: exact native type/MRO and instance dictionaries for `DecodedGLB`, `ReachExecutionWork`, `_Bounds` and `ConstructionBudget`; relevant `read_glb`, `clock_cell_contains`, `rational_clock`, `_Bounds.compare/op`, and work-charge function/code/default/global/builtin bindings; exact `Fraction`, `dict`, `list`, `tuple`, `struct` and native unpack behavior; `work.external_check`, `_source_after_charge`, current `work.tick` identity, construction budget's `check`, trace/profile hooks and reentrant sources; stable binary, accessor layout, selected sampler bindings and uncopied receipt storage. Each actual new inspection must be charged. An exact class check alone, and the unrelated native certificate-term gate, do not establish these conditions for the reader.

Even in the usual `work.tick` → `ConstructionBudget.tick` path, a foreign `check` or observer invalidates the proposed cross-stage inference. Direct calls, monkey-patched functions, subclasses, modified limits and private cache changes must retain ordinary fallback, not be silently discarded. Callbacks and exceptions raised by the literal path keep their original object identity.

### An exact-dict counter can be hostile

`ReachExecutionWork.counts` is an ordinary, externally mutable Python dictionary. `type(counts) is dict` does not establish that reading `counts.get("independent_exact_div")` is callback-free. A foreign key can deliberately share that string's hash; a successful insertion can precede a later hostile `__eq__` method. A fresh native `dict.get` then invokes that method. This was reproduced with standalone Python and the exact key name; the demonstration was not an OntoKin product test.

This concrete aggregate-counter design therefore requires authenticating **all** live dictionary keys as exact native `str` (and bounded native integer counters) at both witness snapshots, or an equivalently strong currently unavailable provenance mechanism. Otherwise malicious comparisons or counter replacement can falsify the eligibility route. The published `_certificate_term_native` routine illustrates such an audit but cannot supply it for free, before it runs, or across an unprotected intervening interval.

### Closed unfavorable cost lower bound for the chosen candidate

Let `N` be selected axis rows; `M` its sampler count; `K0` and `K1` be live category dictionary entry counts at the first and second counter audits; `D` be the total new native dispatch/owner/storage checks; `S` be new creation, publication, lookup, counter read, retirement precharge and type/limit/claim checks. All are nonnegative. This candidate must additionally check each sampler identity (at least `M` new checks); it makes **no** extra `N`-value axis copy.

    H_success >= K0 + K1 + M + D + S
    saved_original_order_charges <= N - 1
    net_saving <= (N - 1) - H_success

These are *lower bounds on added work*, not a fictitious closed upper bound. In the C038 captured failed P16 run, the final genuine category map has **266** entries; its refused adjacent comparator was already a previously used `independent_exact_compare` category. The intervening 160 successful authored comparisons only increment that existing category, so, under the unchanged native category bookkeeping evidenced by C038, the category set is already 266 at the completed row loop. A required **single** full post-row key/type audit would therefore cost at least 266 newly checked categories against **205** gross removable comparisons. Thus for this concrete candidate the most favorable P16 net saving ceiling is at most `205 - 266 = -61`, *before* `K0 + M + D + S`. This is a source-flow inference from C038's complete counter/category reconciliation, not a new live snapshot; it must not be confused with measured optimization performance. If that inference is doubted, the positive `H<205` claim is still unestablished and implementation remains barred.

Across the admitted profile, the separate category metadata cap permits up to 512 categories. Treating a category scan as one unit or silently exempting checked dictionary members would violate adopted accounting. Restricting the gate to a lower category count might define a different eligible subset, but C040 cannot prove it includes P16 and has not closed the other `D,S` terms. A second mutable receipt, full-axis snapshot or per-row guard would need its own complete ledger and cannot be credited here.

### Unsuccessful routes and exception retirement

In a real implementation, a failed native/source/accessor/counter admission must retain every added charge already incurred, then take the **entire original** comparator path. Category checks, source/owner checks, receipt storage and cleanup cannot be hidden as free bookkeeping. On error, cleanup cannot introduce a new callback exception in preference to the original one; proposed precharged callback-free retirement itself requires review. No proof survives a failed request or an exported mutable reader. The limit remains 100,000 shared operations / 30,000 ms / 32,768 operand bits / 256 numerical-cache entries, and the separate 512-category guard is not new allowance.

## Decision and next work

**NO-GO for implementing this exact aggregate-counter + private selected-axis candidate as a P16 optimization.** The immutable-at-origin axis and theoretical order/domain lemmas are plausible, but the authentic counter gate has an unfavorable 266-vs-205 lower bound on the observed P16 source flow. Current-axis/intervening-lifetime native ownership and its full charged schedule are additionally unclosed. No claimed positive generic `H < N-1` exists. This does **not** rule out a separately designed callback-safe, scoped fallback-invalidation witness, nor a different higher-volume optimization elsewhere in the recording pipeline. That would be a **new** scope, not a modification of this rejected witness.

The next agent should use a new isolated branch after this C040 evidence head and choose a high-volume P16 source-level improvement with demonstrable savings **without adding an O(N) or O(K) validation pass**, or separately design a genuinely different scoped fallback-only witness with a complete positive ledger before code.

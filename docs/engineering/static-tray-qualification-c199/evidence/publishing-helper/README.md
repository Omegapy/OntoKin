# Exact GitHub commit import helper

This helper restores a commit object from the authenticated GitHub connector's
`GET /repos/Omegapy/OntoKin/git/commits/<sha>` response. It accepts a saved raw
JSON response or the connector's `structuredContent.content` envelope. It uses
only Python's standard library and local Git commands. It performs no network
operation and never changes a Git reference, branch, checkout or remote.

The default is verification. `--write` adds the exact commit object only after
both the Python implementation and Git compute the requested object identity.
The direct tree and parent commit objects must already exist locally. A write
is followed by an exact byte readback. Import parents before their children.
The helper does not recursively reconstruct missing trees or blobs.

```sh
python3 -IBS /workspace/scratch/801d9d641f68/c199-publishing-helper/import_git_commit.py \
  --repo /workspace/scratch/801d9d641f68/ontokin \
  --metadata /absolute/path/to/saved-git-commit-response.json \
  --sha EXACT_40_CHARACTER_COMMIT \
  --raw-output /absolute/path/to/new-raw-commit-file \
  --report /absolute/path/to/new-verification-receipt.json
```

After reviewing the verified identity, repeat with `--write` and new evidence
filenames. The helper refuses to overwrite existing evidence. Object storage is
content addressed: writing an already present identical object is harmless.
No approval of a branch update is implied by an object write.

## Exact byte issues

GitHub's API may normalize author and committer dates to UTC while the original
Git object retains another timezone offset. An unsigned response therefore may
not contain enough information to reconstruct the original bytes. For newly
created API commits, explicitly supply UTC author and committer dates during
creation. For existing unsigned commits, use offset hints only when supported
by retained raw bytes or other evidence:

```sh
  --author-offset=-0700 --committer-offset=-0700
```

The helper never accepts a guessed candidate whose hash differs from the
requested commit. It considers only the API message and that message plus one
terminal line feed. Any other unsigned header or message discrepancy fails
without writing an object.

For signed commits, `verification.payload` retains the unsigned raw headers,
their order, timezone offsets and message. The helper inserts the API signature
as the folded `gpgsig` header. It preserves a terminal signature line feed and
checks a bounded alternative where the API may have omitted it. The expected
SHA selects the exact header position and newline representation. A signed
payload does not replace cryptographic signature verification; the receipt
reports GitHub's signature result separately from the locally verified object
identity.

## Preparation evidence

`TESTS.json` and `TESTS.log` retain seven passing controls. The original C198
closing commit and signed merge were reconstructed and compared with their
existing local raw objects. Two further CLI verification receipts are retained.
The write control created a synthetic commit in an isolated temporary bare
repository and confirmed that all references and `HEAD` remained unchanged.
No object was written to the root repository by these controls.

The C198 unsigned closing commit requires its original `-0700` offsets. Its API
message has no terminal line feed. The signed C198 merge requires the final
space continuation generated by the signature's terminal line feed. Both raw
objects match byte for byte and reproduce their original Git object hashes.

Keep this helper outside the project source until its review is complete.
Imported unreferenced objects are not automatically retained in a Git bundle.
The final source must reach each required published, lease, merge and closing
commit, or the packager must receive an explicit retained checkpoint reference
for it. This helper deliberately does not create those references.

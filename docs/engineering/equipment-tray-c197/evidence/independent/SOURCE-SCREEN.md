# Independent C197 source screen

**Finding:** the proposal-only closing outcome is appropriate. Existing OntoKin semantics can describe a static reusable tray family, but the inspected repository has no qualified shared construction path for this family.

The core language supplies typed lengths, poses, box geometry, classes, derived values and independent stable occurrences. The construction profile supplies pinned modules and scoped per-instance overrides. The keyed-rack source is a concrete existing example of two roots sharing one definition while one child receives a local override. These are source-level feasibility facts; no tray runtime or export test was run here.

The C193 Blender adapter requires exactly seven gauge parts and two carriage bodies. Its schema rejects additional parts, its source validator rejects a different declaration ID set, and its native worker constructs fixed guide/motor/compound roles from the gauge backend record. A tray translation must introduce a new representation and relationship mapping. C197 explicitly defines that as substantial even if the eventual implementation is small. Renaming gauge roles or changing an experimental namespace would not satisfy admission.

C180 explains why the earlier native OntoKin/Blender workflows are insufficient: a common GLB checker/viewer does not make their separate native exporters a common construction backend. The C183 spacer, C185 rotary and C187 gauge records preserve that distinction. Calling OntoKin's internal exporter from host Python would not establish an existing qualified direct-Blender comparison route.

Reusable GLB decoding exists, but the tray-specific oracle, sibling checks and real delivered-content failure controls still require an independent freeze and qualification. The current task should stop at a versioned bounded proposal, with estimated implementation/validation effort explicitly distinguished from measured evidence. It must not export baselines or dispatch authors.

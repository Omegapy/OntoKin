# C191 validation and evidence boundaries

The adopted [source and backend contract](../../language-design/guided-contact-v0.1/ADOPTION.md)
and [independent frozen expectations](independent/README.md) determine acceptance.
This record explains how the coordinator combines the evidence. It does not
change a numerical limit or turn an unexecuted check into a pass.

## Separate claims

| Claim | Required evidence |
| --- | --- |
| Source meaning | Exact source diagnostics, byte spans, canonical inputs, stable keys, dependency hashes and reviewed admission amendment |
| Native construction | Source-derived body, collider, helper, mass, guide and motor identities inspected in the generated scene |
| Native response | Two fresh builds per A–D case, an independent source rename/reorder build, captured native poses and the disabled-collider causal control |
| Persisted scene | Every successful formal scene reopened in a new pinned Blender process, its cache cleared, and 481 native samples recaptured without reconstruction |
| Recorded geometry and motion | Independent GLB decoding, continuous face-gap and unrelated-pair checks, and frozen analytic checker controls |
| Declared projection | Every native carriage X and timestamp retained in binary32 output; all changed fields enumerated; native-sample and continuous raw-playback bounds no greater than 0.2 mm |
| Failure isolation | Actual bounded supervisor, cancellation and descendant termination; invalid results and publication failures preserve the accepted state and its artifacts |
| Destination readback | Exact raw/final bytes pass Khronos validation and Three.js loading/playback; actual final GLBs are imported into pinned Blender, measured and rendered |
| Legacy compatibility | Existing runtime and historical verification inputs remain byte-identical, the applicable local driver and original conformance run, and documentation preservation passes |

Blender captures evaluated transforms at 240 Hz. Its configured ten substeps per
frame imply 4,800 scheduled substeps over two seconds; the evidence does not
contain direct per-substep Bullet telemetry. Finite-difference velocities and
geometric contact bands are derived from captured poses. They are not contact
manifolds, contact impulses or directly observed Bullet velocities.

The final GLB is recorded animation. It carries neither a live collision solver
nor an executable actuator. A receiving-application playback pass therefore
qualifies the recorded delivery, not live destination physics.

## Independent roles

The reviewer froze the physical expectations and qualified its checker before
inspecting candidate output. It then froze the exact source corpus before
implementation. The coordinator published and read back those inputs before
authorizing semantic implementation. Author development runs remain identified
as development evidence; they do not replace the reviewer's formal fresh builds.

The coordinator checks the receiving applications against the reviewer's exact
artifact hashes. Repeated outputs with identical hashes can share receiving
application evidence, while their native build and reopened-scene records remain
separate. The source rename/reorder case must preserve the physical canonical
input and final output while retaining its different source revision and labels.

## Local driver integrity

The first existing-code driver began on C190 main while the coordinator later
added isolated C191 files to its originating checkout. All 4,252 unit tests and
the source, Agent, construction, surface, impulse and documentation stages
passed. The driver nevertheless failed its originating-input immutability check.
That overall failure is retained; it is not reported as a full driver pass.

A separate audit found that the driver's copied execution workspace retained the
same immutable input inventory throughout. The corrective run uses a detached
C190 checkout that no worker edits. Its result must be recorded as observed.
Before integration, the coordinator compares every inherited tracked input with
that baseline and separately qualifies the newly added prototype. A change to an
inherited runtime or test input would invalidate this eligibility argument.

No hosted Actions run is requested. Local checks establish their recorded
Python/platform and selected roles. They do not satisfy unexecuted compatibility
runs, external release attestations, a production-backend release or the wider
OntoKin goal.

## Failure retention

Keep failed source, development, harness, lifecycle and verification attempts
with their original output. A corrected rerun adds a new record. It must not
overwrite the earlier result or revise the frozen expectation. In particular,
the C191-A1 admission clarification is a separate reviewed dependency; the
original contract manifest remains unchanged.

# Source identity, frozen comparisons and durable compatibility

This document is normative with `OK-LANG-022-CANONICAL-SPIN/0.1.0`.

## Earlier bindings and frozen comparisons

The nine predecessor numerical-basis files remain byte-for-byte identical.
Earlier entry profiles use their original dispatch, complete GLB streams,
metadata, numerical basis and destination behavior. C1 remains whole-byte
comparison without normalization, including padding and provenance fields.

C2 requires the same successful same-program common-clock physical and source
state under this deterministic method; actual work counters, request receipts
and independently identified stores retain their existing comparison rules.
A shared exhausted budget does not become a fresh request allowance.

C3's existing literal neutral .22/legacy expectations remain exact. The six
frozen controls p05/p06/p16/p23/p24/p30 are not edited. Their independent
source-derived stage/stationary proof is part of the new frozen additions.
For the general .22 domain, equality with an earlier profile is excepted only
where the earlier profile chose different constant-spin operands through its
inherited history-dependent plan selection. All other legacy physical,
anchor, translation, source and error obligations remain. This explicit
exception is not a general tolerance or permission to alter a frozen case.
Any literal failure requires a new separately reviewed input/comparison
decision before its expectation can change.

The remaining C4-C6 translation, split-schedule and scoped delivery comparisons
retain their complete original definitions. New metadata identities below
are compared under the appropriate class and do not excuse predecessor bytes.

## Predetermined durable-state policy

The C091 service already binds accepted programs, runs and artifacts to its
actual complete product implementation identity. Adopt the existing mismatch
rules below as the compatibility boundary for this amendment. Do not silently
reinterpret an old .22 run under new arithmetic or rewrite its stored receipt.

| Operation or record | Required behavior across old/new implementation identities |
| --- | --- |
| Same request ID and same canonical payload with an existing persisted response | Return the exact historical response through the existing idempotency route; this is historical output, not a new numerical evaluation. |
| Same request ID with changed payload | Preserve the inherited changed-payload refusal. |
| Queued old request requiring execution | Preserve existing `OKA-E-ENGINE` mismatch handling before current-engine work. |
| Continuation or timed inspection of an old run | Preserve `_check_engine` and its `OKL-E-SAMPLE` refusal; do not reuse the old cursor/anchor as a new-method run. |
| Edit/current operation requiring accepted-engine identity | Preserve the existing acceptance/identity gate and its original diagnostic. |
| Reading an old implementation artifact as a current artifact | Preserve current artifact-integrity/engine checking, including `OKA-E-STORE-INTEGRITY` where the current route already requires it. Historical exact responses remain historical. |
| Validating old-basis GLB bytes as current .22 | Refuse source-basis mismatch with the existing `OKE-E-SOURCE-NUMERIC-BASIS` adapter envelope. |
| Deliberate current validation/reset/fresh evaluation of immutable source | Follow the existing lifecycle under the current implementation, producing separately identified current records; this is not continuation of the old numerical run. |

This policy does not promise support for executing the old method inside the
new service. It retains source, old artifacts and exact original responses as
evidence. Reopen, reset, revision replacement and retries must be exercised
against actual old/current stores before implementation acceptance. Inspect
the actual route before claiming a given old operation is supported; a schema
alone does not establish durable behavior.

Refused current operations preserve accepted programs, runs, artifacts and
their original records. The inherited edit lifecycle may retain a separately
identified unaccepted immutable candidate snapshot for diagnosis before its
engine gate refuses acceptance. Store opening and request handling retain
their existing session/request bookkeeping. This policy does not promise an
unchanged physical database file or prohibit those existing diagnostic rows.

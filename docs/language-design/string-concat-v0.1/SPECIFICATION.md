# C087 bounded pure String concatenation

**Decision identity:** `OK-DEC-STRING-CONCAT/0.1.0`  
**State:** Review draft. Not adopted, published, implemented or validated. Runtime implementation must wait for independent review, complete original-input preflight, and exact publication/readback of the final contract and freeze.  
**Baseline:** C086 main `5d83b07354296a891c1a6acd70efc77322d2127f`, tree `da00e3fe2c36cdd89dbd6e1469eceb1c4400f567`  
**Date:** November 1, 2026 (America/Denver)

## 1. Utility, scope and explicit bindings

The selected expression is `left + right` with exactly two immutable String operands. It computes their ordered Unicode scalar sequence. A reusable component library can compute `prefix + old_key` inside C086 `rekey_keyed`, then combine separately named collections without a per-member literal rename map. This is a concrete composition capability; measured authoring benefit remains unverified.

The selected experimental bindings are source `ontokin "0.20";`, profile `string-concat-0.1`, `ontokin.agent/0.20` and recorded `ontokin.glb/0.20`. Files and immutable bundles remain `ontokin.files/0.2` and `ontokin.bundle/0.2`. The new profile inherits the earlier adopted keyed, geometry, appearance, motion, physics and execution-budget meanings. Ordinary CLI Agent/0.1, Python ProgramAgentService/0.2 and GLB/0.1 defaults remain unchanged.

No new token or precedence level is introduced. `+` keeps its inherited addition precedence and left associativity; parentheses retain their existing meaning. Thus `a + b + c` evaluates `(a + b) + c`, with a separate admission, bound, charge and result reservation at each evaluated String operation. Numeric, quantity, vector and point operations retain their earlier exact types, dimensions, frames and diagnostics.

There is no String interpolation, formatting, numeric/Bool/reference conversion, slicing, splitting, repetition, replacement, parsing, ordering, length API, mutable text, new collection or I/O. `len()` keeps its existing keyed meaning. Computed text does not become a module identity, source ID, import pin, attachment declaration, writable path or patch authority.

## 2. Declaring versions, exact types and static evaluation

The unit declaring the binary expression owns its semantics. String addition is enabled only when that unit declares source `.20` and `string-concat-0.1`. An imported `.19` helper continues to reject String addition even when the entry is `.20`. Older units cannot import `.20` definitions. A `.20` unit may import supported `.2` through `.20` units under existing exact module pins.

Both operand types of the new overload must be exactly `String`. Its result type is exactly `String`. Neither implicit Int-to-Real widening nor another coercion grants String admission. **Only `.20`-declared `String + String` changes.** Every other operator/type pair and every older declaring unit retains the complete inherited dispatch, including its exact successful result or applicable refusal. No uniform String error replaces that dispatch.

For pairs that reach the inherited scalar operator fallback, such as `String + Int`, the refusal remains `OKL-E-TYPE`, category `invalid`, phase `type`, with message `Operator '<op>' is not defined for <left type> and <right type>.`, the complete binary-expression primary span, no related locations and empty details. Earlier vector/point branches retain their distinct messages and precedence: for example, `String + Vec3` retains `A tuple/vector supports multiplication or division by a scalar only.`; `String * Vec3` retains `Vector scaling requires a numeric scalar.` Mixed equality retains its existing compatibility/type/unit rules, including `Incompatible types: ...` where that branch applies. Each independent fixture fixes the applicable inherited result, diagnostic fields and original spans. Numeric, quantity, vector, point, equality and frame behavior are not relabeled as String concatenation.

Global syntax, declaration purity, name/access, type, cycle and inherited unselected-branch checks remain authoritative. Static checking evaluates both operand types under unknown typed locals; it does not use a sample String. In an abstract context, or when either operand has no known payload, a well-typed String addition returns unknown `String`. It performs no byte scan, concatenation allocation, computed-byte reservation or dynamic String stage. This remains true when the abstract children are literal Strings, because the check is about types. Existing expression/type work is still charged.

Invalid empty keyed callbacks and invalid unselected branches fail during inherited static checking. A type-correct unselected branch or never-invoked empty callback performs no dynamic concatenation. Static checks do not acquire permission to evaluate value-dependent numeric domains or hypothetical String allocations.

## 3. Exact value and lexical meaning

The result contains every scalar from the left operand followed by every scalar from the right operand, unchanged. Empty left, empty right and both empty are valid. Equality remains exact; precomposed and combining sequences remain distinct. No normalization, trimming, case folding, escaping or automatic separator is performed.

LANG-001's lexical boundary stays exact: raw UTF-8 scalar text and existing quote, backslash, newline, carriage-return and tab escapes retain their meanings. A backslash followed by `u` remains unsupported syntax. Source locations use original UTF-8 byte offsets. Admission of source/bundles rejects malformed UTF-8 and surrogate code points under its existing rules; C087 introduces no interface for injecting arbitrary Python values as source Strings.

Ordinary String validity is distinct from stable-key validity. A 65-byte ASCII concatenation can be a valid String and an invalid rekey result. Rekey still requires `[A-Za-z0-9][A-Za-z0-9._-]{0,63}` and retains its existing key/collision stages, diagnostics and canonical old-key traversal. Invalid empty, Unicode, whitespace or punctuation-leading keys are not repaired. A constant prefix applied to distinct old keys is injective; collision fixtures use different per-entry prefixes or collisions between separately named collections.

## 4. Dynamic order and the complete-request ledger

Evaluate the left operand once, then the right operand once, using the existing evaluator and provenance capture. A left operand failure stops before the right operand. A right operand failure stops before String admission. After both succeed, enforce the declaring version and exact operator types. Preserve original child exceptions, original diagnostic objects, locations and callback-exception identity.

All stages below use the same actual `SharedExecutionBudget` already authorized for the complete request. There is no second clock, synthetic cancellation object, reset, independent operation allowance or reconstructed authority. Source `.20` belongs to the inherited execution-profile family and requires an explicitly admitted ledger for its exact entry revision. A raw `compile_construction` call without that context retains the existing `execution_context_required` refusal; it does not fall back to `ConstructionBudget` for concatenation. Wrappers temporarily set the ledger stage and restore its prior value in a `finally` block. The original cancellation callback is invoked by the actual ledger tick. A thrown callback object is propagated unchanged.

For two known String operands, the exact operation sequence is:

1. **`string_concat_admission`:** one operation. Poll actual cancellation, operation cap and time before scanning either operand. No computed-result bytes have been reserved.
2. **`string_concat_scan`:** inspect left scalars in order, then right scalars in order, without encoding, joining, concatenating or slicing an operand. Determine one scalar's UTF-8 width from its code point in constant bounded work. Each operand has its own byte counter. Before counting a scalar, charge the number of new 64-byte blocks that the scalar would touch: `ceil((operand_bytes + width)/64) - ceil(operand_bytes/64)`. At most one tick with a positive amount is required for a scalar. The combined byte count then advances by that width. Refuse immediately if the combined count exceeds 65,536. Do not scan later scalars or the later operand after that refusal. Thus cancellation/time checks occur at no more than 64 scalar steps, with at most one scalar-width calculation before the next charge.
3. **`string_concat_allocation`:** after the complete scan passes, charge `1 + ceil(result_bytes/64)` operations in one actual ledger tick. Poll current cancellation/time and operation authority first. Compute `prior_reserved_bytes + result_bytes`; reject a cumulative overflow before changing the counter or allocating the result. Otherwise reserve that entire amount on the same request ledger. This reservation is monotone and is never refunded within a request, including if later publication is cancelled. Only now may the implementation allocate the immutable concatenation payload. A maximum-size copy is bounded by the result cap.
4. **`string_concat_publication`:** one operation after payload construction and before returning its new immutable Value wrapper to the evaluator. Poll actual authority again. Finish all inherited provenance before any Agent publication. Failure publishes no accepted partial result, collection, revision, run or artifact.

Zero-length operands skip only their zero-byte scan charges. All successful known concatenations, including both empty, execute admission, allocation and publication. Implementations may share immutable native storage internally, but they owe the same logical allocation reservation and charges. Success adds exactly

`3 + ceil(left_utf8_bytes/64) + ceil(right_utf8_bytes/64) + ceil(result_utf8_bytes/64)`

operations for this concatenation, beyond inherited operand/type/expression/provenance work. This formula is not a whole-program operation count. A partial failure owes only work actually reached, with the original ledger's debit-before-exhaustion convention retained. The scan can reject at 65,537 through 65,540 bytes depending on the scalar that first crosses the bound; `consumed` records that exact boundary, not a fabricated complete-result length.

The bound is 65,536 **UTF-8 bytes per computed concatenation result**, and the cumulative allowance is 4,194,304 **UTF-8 bytes of logical computed results per complete request**. The latter is attached to the actual shared ledger and survives compiler/evaluation phases inside that request. Retries/reopened stores retain their existing request semantics; a new request obtains its own independently authorized ledger. Repeated doubling, ignored results, empty-identity operations, repeated helper calls and retained results all count when they execute. A repeated reference to an already computed immutable value performs no new concatenation; its inherited read/copy work still applies.

These bounds are selected before candidate performance measurements. The individual cap comfortably supports component names while permitting longer ordinary labels. The cumulative cap admits 64 maximum-sized results, or 65,536 results of 64 bytes if the stricter operation/value limits allow them. In the Python reference, a conservative maximum four-byte scalar representation puts the character storage of all separately allocated computed results under four times the UTF-8 reservation bound, before object headers and already bounded wrapper/provenance structures. This is a bound on this operation's logical result payload contribution, not a total process-memory guarantee. The existing value-entry, expression-depth, source-text, request, inspection-JSON and provenance limits still constrain other storage. Source text's 2,000,000-byte cap and header constants are not used as substitutes for computed-result admission.

Existing authored Strings retain their original limits. Combining an authored String with an empty String still passes through the new bounded scan, so an oversized operand is rejected before result allocation. A higher operation/time request does not enlarge these byte caps. A caller can only lower operation/time authority; independently current host ceilings remain necessary for higher source requests. Ordinary defaults remain 100,000 operations and 30,000 ms. Modeled animation duration remains separate.

## 5. Exact new resource diagnostics and precedence

Both new String resource refusals use `OKL-E-RESOURCE`, category `resource_limit`, phase `support`, rule `LANG-009`, and the original complete binary-expression span as primary. Grouping parentheses enclosing that expression are part of its inherited full span. They have no related locations. Details contain exactly the four fields below; no actual Strings or hypothetical full encoding is needed to report them.

| Boundary | Exact message | Exact details |
| --- | --- | --- |
| Individual result | `String concatenation exceeds 65536 UTF-8 result bytes.` | `{"budget":"string_concat_result_bytes","limit":65536,"consumed":<first excessive scalar boundary>,"profile":"string-concat-0.1"}` |
| Request total | `String concatenation exceeds 4194304 cumulative UTF-8 result bytes.` | `{"budget":"string_concat_total_bytes","limit":4194304,"consumed":<prior reservation + this result>,"profile":"string-concat-0.1"}` |

The repair text is exactly `Reduce computed String sizes or the number of concatenation results in this request.` Inherited operation/time failures retain their existing code, phase, details, message, reason and actual String stage. Cancellation retains the original exception identity and established Agent mapping. No String error catches and replaces an original child error or exhaustion.

Precedence is inherited static validation, left operand failure, right operand failure, exact operator/type admission, admission-stage authority, scan-stage authority and first per-result overflow, allocation-stage authority, cumulative overflow, actual bounded allocation, publication-stage authority, then downstream consumer checks. Authority can interrupt before a later semantic refusal. Per-result overflow prevents a cumulative check; a cumulative overflow prevents allocation/publication. A concatenation that succeeds but violates stable-key syntax retains the downstream C086 rekey error.

## 6. Caches, detached provenance and purity

No computed-String result cache, persistent concatenation cache or constant folding of concatenation is introduced. A `.20` source `+` expression is conservatively ineligible for existing constant/parameter value caches; syntax-only classification caches remain permitted. An enclosing expression whose cache would skip such a node is ineligible too. This rule is based on the expression's declaring unit, not the entry profile, so imported older numeric definitions keep their existing cache routes. A `.20` numeric `+` may also conservatively miss these caches because classification must not execute operands to guess their types; its inherited numeric semantics remain unchanged. All other unaffected older/profile routes retain their exact caches.

Helper calls execute their selected bodies normally and pay each actually reached concatenation. A cache hit for an operand value cannot exempt the enclosing concatenation's admission, scan, allocation or publication. No type-check or unknown-value path may populate a known concatenation result. Warm/cold helper and repeated-reference fixtures distinguish reuse of already computed values from re-execution of an expression.

The inherited expression caches do not accept user-defined helper calls: their call allowlists contain only fixed builtins and immutable constructors, and shadowing guards retain their current authority. Parameter replay accepts only actual `param` members, not derived members. A parameter/default/derived member can itself have computed text through a helper; its first guarded binding evaluates the helper and pays every actual concatenation, then retains that immutable binding under the existing member semantics. Every later read replays dependency, generated-taint and request-budget guards without reconstructing that binding. Reading an established binding is not a new concatenation. An enclosing eligible expression may reuse its value only after those actual parameter reads; it cannot skip a helper invocation that ordinary evaluation would otherwise perform. These boundaries require explicit warm-call, member-default, derived-member and condition-only dependency fixtures.

The existing expression-flow machinery combines both actually evaluated operand dependencies and taints in order, with the inherited deduplication rules. There is no new public concatenation lineage schema. Preserve every map/reduction/filter/merge/zip/rekey origin and all actual member/definition dependencies, including when a later operation discards the text or uses an empty operand. Preserve forbidden generated-value taints and exact source revisions. Unselected dynamic branches contribute no invented reads; static checks remain separate.

When concatenation feeds rekey, C086's seven-field rekey lineage still records original old/new keys and original payload entries. Earlier zip/rekey contributor keys are never rewritten to a later computed key. Original `.ok` spans and immutable current revisions remain the only repair authority. Changing a prefix removes/adds the affected generated keys; sibling occurrences, surviving keys, payloads, libraries, PNG bytes and independent motion remain unchanged unless their actual source changed.
